# 手动把 `app.asar` 换回官方原版（RESTORE-STOCK）

> 适用：备份没了、不想用插件的还原功能、或者你根本不信任这台机器上的 asar 当前状态。
> 只需要**文件管理器**和**一个能打开安装包的压缩工具**；不需要装 DSH 以外的任何程序。
>
> 标注：**[实测]** = 在本机 `0.2.2-rc.3` 上亲手跑过或量过；**[推断]** = 本机无法确认，
> 按文中的检查步骤自己核对；**[官方]** = 官方发布物的说法。

## 什么时候需要这一步

下面任一情况，都可以照这份文档手工作业：

- `resources\` 里**没有任何** `app.asar.*.bak`，而 asar 已经不是官方字节（比如 DSH 升级把备份一起删了、
  或者你自己清理过旧文件）；
- 备份还在，但你不想用它——想直接从官方安装包里取一份"厂家发的那一份"；
- 托盘或桌面版行为看着不对，想先把 asar 恢复到确定的状态，再重新判断问题出在哪。

如果只是**用完插件后想收摊**，先别急着手工操作——分两种情况：

- 如果是**当前布局**（「官方槽位 + 自有区域」），设置页 → 本插件 →
  「卸载 / 还原 asar…」会做**反向手术**：把插入的那段区域连同被后移的数据整体退回去，
  **不需要任何备份**，产出的就是官方原档（本机实测逐字节等于 `14cfd81c…25ae` / 209,021,953 字节）。
  DSH 运行中也能完成。要退回的是**磁盘上实际那段区域的长度**——当前装出来是 16,384 字节，
  但更早的构建可能装过别的长度；反向手术按文件里的几何算，不认这个常数。
- 如果是**更早版本装的**（「槽位内补丁 0.1.x」），官方字节已经**被替换**了，那就只有备份能换回来：
  插件的还原会用安装记录里那份官方摘要去找备份，找不到才会报"无法还原"，那份备份也丢了就
  回到本文的手工流程。

> **一句话**：本文是**最后手段**。当前布局的正常卸载不需要它，也不需要备份；它存在的理由是
> 「备份没了 + 装的是 0.1.x」或「区域本身被改坏了，反向手术算不回去」这两种情况。

## 补丁到底改了什么（以及为什么换回文件就能好）

**两种布局，两种改法**。先弄清这台机器是哪种——命令行跑一次
`node scripts/install.mjs --status --root <安装目录>` 会打出一行「布局：…」
（`官方槽位 + 自有区域 0.2.0` / `槽位内补丁 0.1.x` / `官方原样` / `重复安装（需还原）`，
`--json` 里字段名是 `layout`）。

### 当前布局：官方槽位保持原样 + 插入自有区域（[实测]）

1. **官方 `lib/main.js` 里托盘那段代码（1,253 字节）一个字节都不动**；
2. 在它**后面**插入一段我们自己的区域，里面是"去加载外置桥文件"的实现；因为插进了字节，
   `lib/main.js` 变长**正好等于区域长度**，它后面的 29 个条目（993,917 B）与 `lib/main.js`
   自己的 67,863 B 尾部**整体后移同样的字节数**，30 个目录字段被改写；
   **区域长度是可变的**：当前预留 16,384 字节，更早的构建可能装过别的长度——反向手术按
   文件里的几何算，不认这个常数；
3. 归档因此比官方原档大**一个区域长度**（当前是 16,384 字节：209,021,953 → **209,038,337** 字节，
   rc.3 实测）；**目录头的长度保持不变**（5,669,961 B 进、5,669,961 B 出），所以
   `integrity.blocks` 一个都没动；
4. 在 `resources/app.asar.unpacked/dsh/tray-bridge.js` 放一个外置桥文件；
5. 安装前在同目录留一份官方原样的备份（不是卸载必需的，是"手术中途崩掉"时的后路）。

**为什么这台机器上"官方原来写的那段代码"还在**：插入**没有**改它，只是把它后面的东西挪了位置。
所以"痕量"只在插入的那段区域与随之平移的数据；把它撤掉，文件就回到原样。

### 0.1.x：等长替换那个槽位

> 只有早年装过的机器会处于这种布局；插件认得它，第一次「安装」会自动迁移到当前布局
> （迁移要用到那份备份）。下面这条路径仍然保留，因为迁移失败的机器要能手工回去。

1. 在 `app.asar` 的 `lib/main.js` 里，把**托盘那一小段代码**（1,253 字节）等长替换成"去加载
   外置桥文件"的实现。改前改后字节数完全相同，所以 asar 的大小、目录头、全部 offset 都不变；
2. 在 `resources/app.asar.unpacked/dsh/tray-bridge.js` 放一个外置桥文件，主进程运行时去加载它；
3. 安装前在同目录留一份官方原样的备份。

**这一种"恢复原版"只有一个动作**：**把那 1,253 字节换回官方的写法**。官方安装包里的 `app.asar`
就是没被动过的那一份，直接盖回去即可；覆盖之后 asar 里再没有任何代码去加载桥文件，
旁边那个 `tray-bridge.js` 留着也不会被读取（想清干净可以手工删掉，见文末）。

### 如果托盘不见了 / 到底发生了什么

一句话版本：**插件只在一处做文章——要么替换 `lib/main.js` 里托盘那段代码的字节（0.1.x），
要么在它后面插入自己的区域（0.2.0）；别的东西不换**。
那段代码原来的工作，是"建一个托盘图标 + 挂那三项菜单"；装过插件之后，它做的是同一件事，
只是先试着去加载 `app.asar.unpacked\dsh\tray-bridge.js`，加载失败就自己画那三项
（`try/catch` 兜底在你看到这个现象之前就已经兜住了）。

所以：

- **桥文件被删、被换、或版本对不上 → 托盘仍然在**，菜单退回官方三项。这是补丁自带的行为，
  不需要你修，也不该成为"换回官方 asar"的理由；
- **托盘真的不见了 → 出问题的不是桥，而是那段托盘代码本身**：要么 asar 被别的工具改成了
  解不开的样子，要么 asar 与主程序版本不配套（**[推断]**：这是从"桥坏了托盘仍在"反推出来的
  剩余可能；本机没有复现过"整条托盘消失"）。
  **把官方那份 `app.asar` 盖回去就能覆盖这两种情况**——官方字节里那段代码是官方自己的写法，
  不依赖任何外置文件；
- 反过来，**不要**为了让托盘回来去删 `tray-bridge.js` 或改状态目录：那些动作不会把 asar 里
  被改掉的字节变回官方写法（0.2.0 是撤掉插入的区域），只会让你丢掉诊断信息
  （`bridge.json` / `bridge.load.json` 是判断"桥到底有没有被加载"的证据，见 `TECHDOC.md` §7）。

## 前置条件：先完全退出 DSH

`app.asar` 是 DSH 运行期间**保持打开**的文件，所以运行中替换它**可能**因为"文件被占用"而失败
（共享冲突），也可能只写进去一部分。插件自己就是按这个事实设计的：它在 DSH 运行时还原走的是
"同等大小、原位分块覆盖"，而不是先删后写（见 `TECHDOC.md` §12）。手工作业没有那套兜底，所以：

1. 在 DSH 托盘的右键菜单里选退出（不要只点窗口右上角的 ×，那只是收进托盘）；
2. 打开任务管理器，确认**没有残留的 `DeepSeek Harness.exe` 进程**（本机进程名就叫这个，[实测]；
   正常运行时有多个同名进程是正常的，它们属于同一个应用，并非"残留"）；
3. 有残留就结束掉，再继续。

替换文件时 DSH 必须**完全关闭**；这条没有例外。

> 顺带提醒一个真实的坑：**DSH 就是你正在看这个界面的那个程序**。关掉它，这个会话也会断。
> 更省事的做法是先把这份文档读完、把安装包和压缩工具都准备好，再一次性退出、覆盖、重开。

## 步骤

### 1. 拿到与已安装版本一致的官方安装包

版本必须对得上。查版本最快的方式：右键安装目录里的 `DeepSeek Harness.exe` → 属性 → 详细信息，
看「文件版本」（本机是 `0.2.2-rc.3`，[实测]）。

**先别急着下载。** 如果这台机器是走自动更新升上来的，安装包很可能**已经在本地**（[实测]）：

```text
%LOCALAPPDATA%\@deepseek-aidsh-desktop-updater\pending\deepseek-harness-<版本>-win-x64.exe
```

本机实际路径与大小：

```text
%LOCALAPPDATA%\@deepseek-aidsh-desktop-updater\pending\deepseek-harness-0.2.2-rc.3-win-x64.exe
299,595,752 字节
```

大小对得上就直接用它，省一次两百多兆的下载。没有的话再下载同一版本的安装包。

两个能对照的旁证（都不必真去读，知道存在即可）：

- 安装目录里的 `resources\app-update.yml` 写了下载源与通道（本机 `channel: nightly`，[实测]）；
- asar 内部 `package.json` 的 `version` 必须与主程序的「文件版本」一致——插件每次看 asar 都会
  读它，设置页「DSH 版本」那一行显示的就是这个值。

> 拿错版本会得到一份"和主程序不配套"的 asar。宁可多下一次，也不要拿别的版本的 asar 顶上去。

### 2. 用压缩工具打开安装包

Windows 自带的资源管理器**打不开这种安装包**（它是 NSIS 安装程序，不是 zip）。
用一个能把安装程序当压缩包打开的工具有：7-Zip 即可（WinRAR、Bandizip 一类通常也行）。
在工具里选「打开压缩包」/「Open archive」，指向那个 `.exe`，**不要**双击运行它
（双击就是启动安装程序，那是另一件事，不是本流程要的）。

> 本机**没有装**带右键菜单的 7-Zip（两个标准安装路径
> （`<Program Files>\7-Zip\7z.exe` 与 `<Program Files (x86)>\7-Zip\7z.exe`）都不存在，[实测]），
> 所以本文"在压缩工具界面里点着打开"的那几步**没有**在 7-Zip 的图形界面上逐步走过。
> 不过**整条路径是用命令行 7-Zip 完整跑通的** [实测]，见第 3 步；机器上随别的软件附带的
> 命令行 `7z.exe` 就够用（本机实测可用的是
> `<7z.exe 路径>`，版本 26.01）。

命令行可以完全省掉点界面这一步（下面三条命令本机实测跑过）：

```powershell
$z = '<7z.exe 路径>'   # 换成你自己机器上的 7z.exe
$exe = '%LOCALAPPDATA%\@deepseek-aidsh-desktop-updater\pending\deepseek-harness-0.2.2-rc.3-win-x64.exe'
$out = '<临时目录>'                                   # 解到安装目录之外的任意可写目录

# 1) 列出安装包内容，确认有 $PLUGINSDIR\app-64.7z 这一行（298,410,282 字节）
& $z l $exe

# 2) 把这一层取出来（-o 后面不带空格；$PLUGINSDIR 用单引号，免得被 PowerShell 当变量）
& $z e $exe '$PLUGINSDIR\app-64.7z' "-o$out" -y

# 3) 再从它里面取出 asar
& $z e "$out\app-64.7z" 'resources\app.asar' "-o$out" -y
```

> `$out` 可以不存在——7-Zip 会自己建目录（[实测]）；`D:` 只是示例，换成本机任意可写盘符
> 或 `$env:TEMP` 下的目录都行。不要解到 `<盘符>:\` 根目录或 `<Program Files>`：普通账户写不进去。

### 3. 在安装包里按路径找到原版 asar

路径是：

```text
<安装包>\$PLUGINSDIR\app-64.7z\resources\app.asar
```

拆开读：安装包里有一个 `$PLUGINSDIR` 目录（名字里的 `$` 是它的一部分，不是变量），
里面有 `app-64.7z`；这个 7z 里才是真正的程序文件，其中一条是 `resources\app.asar`。

**这条路径整段在本机核对过 [实测]**，用的是
`deepseek-harness-0.2.2-rc.3-win-x64.exe`（299,595,752 字节）。每一层看到的东西：

| 层 | 看到的东西 |
| --- | --- |
| 安装包（NSIS-3 Unicode） | 共 15 个条目；其中 `$PLUGINSDIR\app-64.7z` 一行写着 **298,410,282 字节** |
| `app-64.7z` | 顶层 19 条，含 `DeepSeek Harness.exe`、`locales\`、`resources\`、`resources.pak` 等 |
| 里面的 `resources\` | 8 条：`app.asar`、`app.asar.unpacked\`、`app-update.yml`、`default_app.asar`、`elevate.exe`、`icon.png`、`runtime\`、`tray.ico` |
| 里面的 `resources\app.asar` | 文件条目写着 **209,021,953 字节**；解出来算摘要 = **`14cfd81c…25ae`** |

最后那个摘要与已安装的 `0.2.2-rc.3` 登记的官方摘要（`lib/wire/shells.js` 的 `KNOWN_SHELLS`）
**逐字符相同**，这就是"取到的是官方原版"的证据 [实测]。上面这四行不是读代码推出来的，
是按第 2 步那套命令一条条跑出来的。

所以 `$PLUGINSDIR` / `app-64.7z` 这两个字面名字在本机这份安装包上是**真实存在**的，不是凭惯例猜的。
换一个发布、换一个架构，这两层的显示名可能不同（32 位构建大概是 `app-32.7z`，**[推断]**，
本机没有 32 位安装包可查）。**不要凭名字认**，用下面三条判断：

- 那一层是一整段两百多 MB 的 7z（本机 298,410,282 字节，[实测]）——几 MB 的肯定不是；
- 打开它以后顶层能看到 `DeepSeek Harness.exe`、`locales\`、`resources\`、`resources.pak`
  （本机顶层 19 条，[实测]）；
- `resources\` 恰好是上面那八条（[实测]）。其中只有两个是目录（`app.asar.unpacked\` 与 `runtime\`）；
  `app.asar.unpacked\` 之下登记了 **1,992** 条路径：一条是 `dsh\` 本身，其余全在
  `dsh\node_modules\…` 里（[实测]）。

> 这三条不是让你背下来，而是让"我打开的到底是不是那个 7z"变成一个**可回答的问题**。
> 只要 `resources\` 那八条对得上，你就站在正确的层上了。

**一个能自我验证的判据**：官方 `resources\app.asar` 解出来必须是该版本登记的
**字节数 + SHA-256**（`0.2.2-rc.3` 是 `209,021,953` 字节 / `14cfd81c…25ae`），见第 5 步。
解错了版本、解错了层、或者解成了 `app.asar.unpacked` 里的某个文件，这一步就会当场对不上。

> 官方安装包里**没有**插件的 `tray-bridge.js`（本机核对过它不在内嵌 7z 的路径表里，[实测]）。
> 这也是"官方那份一定没被本插件改过"的证据之一。

### 4. 取出 `resources\app.asar`

在压缩工具里选中 `resources\app.asar`，解压到**安装目录之外的临时位置**（例如 `<临时目录>\`）。
不要直接"解压到安装目录"——那会把同版本的一整套文件都铺上去，没有必要，也更容易出事。

解出来的 asar 本身约 **209 MB**（`0.2.2-rc.3` 是 209,021,953 字节）。中间还要先放下取出来的
那一层 7z（本机 298,410,282 字节），所以临时目录按 **600 MB 以上** 留比较稳妥（这是个估算，
不是硬指标）。

### 5. 核对解出来的文件（字节数 + 摘要）

在覆盖之前先证明手里这份是对的。两个都过才算过：

- **字节数**必须是该版本官方发布的数值（`0.2.2-rc.3` 是 `209,021,953`）；
- **SHA-256** 必须等于该版本的官方摘要（`0.2.2-rc.3` 是
  `14cfd81c9135bf0afb89417543c94f9ecfe09266574452a9b106890c698725ae`）。
  这个值登记在 `lib/wire/shells.js` 的 `KNOWN_SHELLS` 里（`0.2.2-rc.3` 那条的 `archiveSha`）。

```powershell
# PowerShell（只读两个值）
$f = '<临时目录>\app.asar'
(Get-Item -LiteralPath $f).Length
(Get-FileHash -LiteralPath $f -Algorithm SHA256).Hash
```

```bat
:: cmd
certutil -hashfile <临时目录>\app.asar SHA256
```

两个命令的**大小写不一样**：`Get-FileHash` 输出大写，`certutil` 输出小写（本机都实测过，[实测]）。
所以比对时按十六进制逐字符比，忽略大小写即可。

### 6. 覆盖安装目录里的 `app.asar`

把解出来的 `app.asar` 复制到 `<安装目录>\resources\`，**文件名保持 `app.asar`**
（本机即 `<DSH安装目录>\resources\app.asar`）。同名覆盖，不要改成
`app.asar.new` 之类——Electron 只认这个名字。

**不要动 `app.asar.unpacked`**：它是 asar 之外的另一棵树，官方那份与已装的差别只在于多了一个
插件放进去的 `dsh\tray-bridge.js`。本流程只替换 asar 这一个文件。

覆盖失败、提示"文件正在使用/共享冲突"，说明「前置条件」没做完——回去确认进程真的没了，再试一次。

### 7. 再核对一次磁盘上的文件

**用摘要核对，不要用时间戳。** 覆盖成功和"看起来像覆盖成功了"是两件事：

```powershell
# PowerShell（只读两个值）
$f = '<DSH安装目录>\resources\app.asar'
(Get-Item -LiteralPath $f).Length
(Get-FileHash -LiteralPath $f -Algorithm SHA256).Hash
```

期望：`209,021,953` 字节、`14cfd81c…25ae`。对不上就回去重做「前置条件」和第 6 步，
或先停在原地找人看，**不要**启动 DSH。

### 8. 启动 DSH，确认状态

重新打开 DSH，进 设置 → 插件 → 本插件，卡片上的「状态」应显示 **「官方原样（可安装）」**。
看到这句话就说明 asar 已经是官方字节了。

## 捷径：同目录已经有官方原样的 `.bak`

如果 `resources\` 里还留着 `app.asar.<时间>.v<版本>.bak`，先别下载安装包——验证一下它：

```powershell
Get-FileHash -LiteralPath '<DSH安装目录>\resources\app.asar.20261114-2125.v0.2.2-rc.3.bak' -Algorithm SHA256
```

本机这份备份实测输出 `14CFD81C…25AE`、209,021,953 字节，与官方值一致（[实测]）。

- 摘要等于官方值（`14cfd81c…25ae`）→ **这份 `.bak` 就是官方字节**，直接把它复制成
  `app.asar`（同目录、同名覆盖）即可，省掉下载和解压；
- 摘要不等 → 它不是当前版本的官方原样，别用它当源，回到上面的完整流程。

同目录有多个 `.bak` 时逐个算摘要：认摘要，不认新旧，也不认文件名里的时间戳。

> 这也正是插件自己还原时用的判据（`findBackup` 优先安装记录里的摘要）；
> 手工作业时你在扮演同一个判断，所以判据必须一样：**只看摘要**。

## 常见陷阱

- **运行中的 DSH 会锁住 asar。** 没完全退出就覆盖，轻则失败，重则写进去半截。退出后必须确认进程没了。
- **杀软/安全软件可能拦下写入，或者悄悄保留旧文件的句柄。** 现象是"复制成功"但内容没变。
  所以第 7 步一定**比摘要**：别信时间戳，也别只信大小（大小相同正是这种情况的特征）。
- **拿错版本。** 装的是 `0.2.2-rc.3`，就不要用 rc.2 或别的版本的 asar 顶替。
- **拿错了工具/层。** 资源管理器打不开 NSIS 安装包；别在资源管理器里反复双击那个 `.exe`（那会启动
  安装程序）。解到 `app.asar.unpacked` 里的某个文件也不算数——第 5 步的字节数是最好的一票否决。
- **以为要连 `app.asar.unpacked` 一起换。** 不需要，而且不该——本流程只替换一个文件。
- **只解压、不覆盖。** 解出来的文件在 `<临时目录>\`，安装目录里那份旧 asar 还在，什么都没发生。

## 换回之后，插件会怎么反应

asar 回到官方字节后，插件检测到的状态是「官方原样（可安装）」——官方槽位与区域标记都没有了
（0.2.0 下还会核对 `layout` 是否回到 `pristine`），所以它**会再次认为"需要安装"**，
安装页可能再弹一次。处理方式：

- 不想再装 → 在插件页**禁用本插件**；安装页按「稍后」只闭嘴到本次运行结束，重启还会问；
- 想继续用 → 正常点「安装」，它会重新判断版本、复用或新建备份、再插入一次区域
  （首次安装会再搬一次约 1 MB；如果你手工换回原档后点安装，`layout` 是 `pristine`，
  走的正是首次安装那条路）；
- 手工删掉 `resources\app.asar.unpacked\dsh\tray-bridge.js` 也无害：官方 asar 不会去加载它，
  删它只是让文件树更干净（要删就删这一个文件，不要删整个 `dsh` 目录——那里的
  `node_modules` 是官方发布的）。

删除 `.bak` 备份**不会**破坏已安装的状态，只是少了一条回官方字节的路。
**0.2.0 的 split 布局尤其不怕**：它的卸载走反向手术，`.bak` 删光了也照样能还原。

## 顺手可以做的：先让插件自己试一次

在动手解安装包之前，先确认这台机器是哪种布局（`node scripts/install.mjs --status --root <安装目录>`
的一行「布局：…」，或者设置页 → 本插件 → 状态与还原按钮）：

- **`官方槽位 + 自有区域 0.2.0`** → 点「卸载 / 还原 asar…」。它走反向手术，**不需要备份**，
  即使 `resources\` 里一个 `.bak` 都没有。成功之后 asar 大小应回到 **209,021,953 字节**、
  摘要回到 `14cfd81c…25ae`（本机 rc.3 实测）。这一步失败或算出来的摘要对不上，
  插件会**如实报错**并回落到备份（备份也没有才是真正的"走本文"）；
- **`槽位内补丁 0.1.x`** → 同上，但它是用备份还原的；备份没了就是本文的用武之地；
- **`官方原样`** → 什么都不用做，插件会说「无需还原」。

> 换句话说，本文在 0.2.0 下是**第二手段**，第一手段是插件自己的反向手术。先试它，
> 省一次两百多兆的下载与解压。

## 为什么插件不自己干这件事

当备份没了、asar 又已经被改过时，插件手里**没有官方字节**——**除了 0.2.0 的 split 布局**：
那种布局下官方字节可以从文件自身的几何**反算**出来（把插入的区域与后移的数据退回去），
所以插件能自己干，也确实干了（`shrinkRegion`）。

但这条反算有个前提：文件里的几何还得是它当初写下的样子。区域被手工改过、`lib/main.js`
的目录 `size` 与字节数不符、目录头不能逐字节往返序列化……这些情况下反向手术会**拒绝**（
它的所有数值判断都在写第一个字节之前），那时插件手里就真的没有官方字节了。
把它复制一份再标成"官方原样"，会把"这机器上没备份了"变成"这机器有官方备份了"——那比没有更糟，
因为它让下一次还原把一份错的东西当正确答案写回去。所以插件这时只做一件事：如实报告
"基线不可恢复"，把拿回官方字节的办法交给人（也就是这份文档）。

能提供官方字节的东西有三样：**反向手术**（0.2.0，从当前文件反算）、
**同目录里摘要是官方值的那份 `.bak`**、或者**官方安装包里的那份 asar**。
最后一条是兜底，也是唯一不依赖本机历史状态的来源。
